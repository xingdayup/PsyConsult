# Part 02｜第一次跑起来：先见结果，再认技术

## 学习目标

按“准备环境 → 直接问专家组 → 经过接待窗口 → 打开医生工作台”的顺序完成第一次运行，并知道每一步成功时应看到什么。

## 生活类比：门诊试营业

新门诊不会第一天就让所有岗位同时接待患者。更稳妥的做法是：先检查水电和钥匙，再让专家内部试诊，然后测试接待窗口，最后开放医生工作台。本篇也按这个顺序排障。

## 图解

```text
① 环境就绪
    ↓
② 专家组内部试问（CLI）
    ↓
③ 接待窗口收发信件（API）
    ↓
④ 医生工作台完整体验（浏览器）
```

## 分步骤体验

1. [环境准备](environment.md)：确认 Python、配置和资料服务；
2. [第一次 CLI](first-cli.md)：绕过网页与接口，直接验证专家组；
3. [第一次 API](first-api.md)：理解一次请求如何装进“信封”；
4. [第一次浏览器体验](first-browser.md)：观察工作台如何逐步展示结果。

每一步只增加一层。当前一步失败时，不要急着进入下一步。

## 项目真实实现

四步对应真实入口：

| 体验 | 入口 | 主要验证什么 |
|---|---|---|
| 环境 | [`agent/.env`](../../agent/) 与 [`docker/`](../../docker/) | 依赖和连接条件 |
| CLI | [`agent/main.py`](../../agent/main.py) | 模型、图和资料能力 |
| API | [`app/router/chat.py`](../../app/router/chat.py) | 身份、请求与流式响应 |
| 浏览器 | [`front/clinical_cds/`](../../front/clinical_cds/) | 完整用户体验 |

Redis、Milvus、Neo4j 不可用时部分能力可降级，但模型密钥必须有效，缺失资料也会影响结果质量。

## 源码二刷

第一次只看现象；跑通后再按入口重读：

1. CLI 参数如何变成内部状态；
2. API 如何从 Header 和 Body 取值；
3. 浏览器如何复用 `session_id`；
4. 服务端如何持续送出多段 `data:`。

对应文件是 [`agent/main.py`](../../agent/main.py)、[`app/router/chat.py`](../../app/router/chat.py)、[`app/service/chat_service.py`](../../app/service/chat_service.py)。

## 面试背板

> 我用分层冒烟方式验证系统：先在 CLI 验证 Agent 核心，再用命令行请求验证 HTTP 和流式协议，最后验证浏览器交互。这样能把模型/图故障、接口故障和页面故障快速隔离，而不是看到“页面没反应”就盲目排查所有层。

## 常见问题

**可以直接打开浏览器吗？** 可以，但失败时很难判断是哪一层的问题，初学者更适合按顺序验证。

**基础服务必须全部启动吗？** 单轮推理设计为可降级，但完整体验建议启动 Redis、Milvus 和 Neo4j。

**练习会产生费用吗？** 模型和向量接口可能产生调用费用，请使用自己的密钥并控制次数。

## 自测

1. 为什么 CLI 应在浏览器之前验证？
2. API 体验比 CLI 多验证了哪一层？
3. 哪一步最接近最终用户？
