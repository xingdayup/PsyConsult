# 06 上下文工程：短期窗口 + 历史摘要

> 学习目标：讲清楚为什么多轮消息不能无限累积，以及压缩节点的完整实现细节（阈值、摘要提示词、RemoveMessage 重放）。
> 状态：骨架已含全部要点与代码锚点，叙述性文字待补。

## 1. 问题：checkpoint 让消息只增不减

有了 checkpoint，每轮 2-4 条消息进 state。临床会话可能几十轮，代价有三：
- **token 成本**：每个领域节点都把全量 `state["messages"]` 拼进 prompt，线性膨胀
- **延迟**：长上下文推理变慢
- **信噪比**：早期寒暄稀释关键临床信息

v1 的解法是硬裁剪（>10 条砍到最近 6 条）——直接丢信息，病例细节消失（第 09 章的痛点之一）。

## 2. v2 解法：压缩节点（`graph_manager._compress_history`）

常量：`HISTORY_COMPRESS_THRESHOLD = 16`（超过才触发）、`HISTORY_KEEP_RECENT = 8`（保留最近 8 条）

流程：
1. 消息数 ≤ 16 → 返回 `{}`（no-op，零开销轮次）
2. `old = messages[:-8]`，`keep = messages[-8:]`
3. LLM 摘要 old（提示词要求保留：主诉与症状、持续时间、量表分数、诊断结论、用药方案、工具检索到的关键知识、医生偏好）
4. 返回消息操作列表：
   ```python
   [RemoveMessage(id=m.id) for m in messages]   # 全部移除
   + [SystemMessage("【历史会话摘要】...")]       # 摘要置前
   + keep                                        # 重放保留窗口
   ```
5. add_messages 处理：按 id 删除 → 追加摘要与保留消息 → 实现可控排序

**实测效果**（第 10 章）：19 条 → 压缩后 [8 条保留 + 1 条摘要]，摘要完整保留了最初病例的主诉/症状/PHQ-9——原始消息删了，信息没丢。

## 3. 设计细节与取舍

- **为什么是图节点而不是调用前拦截**：图节点对所有入口生效（Web / CLI / 未来的定时任务），且享受同样的 checkpoint 语义
- **为什么阈值 16 / 窗口 8**：临床流水线单轮最多产生 4 条消息（1 问 + 3 节点输出），16 ≈ 4 轮完整对话后触发，8 = 2 轮近事全保留；数字可调，先拍后验
- **摘要 LLM**：与推理 LLM 同配置但 `temperature=0`（确定性）
- **失败降级**：LLM 摘要抛错 / 消息缺 id → 返回 `{}` 不压缩，本轮全量继续（不阻塞主流程）
- **已知次优**：摘要消息在最终序列里位于保留窗口之后（reducer 处理顺序所致），功能无影响、排序非完美
