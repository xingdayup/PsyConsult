# 02｜临床边界：系统递材料，医生作决定

## 学习目标

能清楚说出三条底线：系统不替代临床判断，紧急风险不等待模型，学习环境不使用真实患者数据。

## 生活类比：会诊记录不能代替签字

医院会诊时，其他科室可以给出意见，但主管医生仍需结合完整病史、检查与现场情况作决定。PsyConsult 更像一份自动整理的会诊草稿：它可能遗漏、误解或引用过时材料，因此不能直接变成诊断书和处方。

## 图解

```text
系统可以做                         系统不能做
────────                         ────────
整理症状与待补信息                 宣布最终诊断
给出鉴别和治疗参考                 自动开药或调剂量
提示可能的药物风险                 保证没有遗漏
展示检索到的资料                   取代急救与危机流程

              最终都要经过临床人员复核
```

## 分步骤体验

面对虚构病例时，按以下顺序判断：

1. **先看紧急性**：自伤/他伤、意识障碍、严重不良反应等情况应立即进入当地急救或危机流程；
2. **再看信息完整性**：病程、既往史、物质使用、躯体疾病等缺失时要明确追问；
3. **最后看建议**：把输出当核对清单，不当结论；
4. **处理数据**：练习只用 [`mock_data/`](../../mock_data/) 或自行编写的虚构病例。

## 项目真实实现

工作台明确展示“仅供临床参考”的提示，见 [`front/clinical_cds/src/App.vue`](../../front/clinical_cds/src/App.vue)。后端限制请求字段和身份格式，见 [`app/schemas/chat.py`](../../app/schemas/chat.py) 与 [`app/router/chat.py`](../../app/router/chat.py)。

但这些工程措施不等于完整医疗安全体系：

- `X-User-Id` 是原型中的调用者标识，不是医院级身份认证；
- Bearer Token 只有在后端配置 `API_AUTH_TOKEN` 时才强制；
- Redis Checkpoint、Milvus 缓存与长期记忆可能保存输入或提取内容；
- 当前系统没有医疗器械认证、生产级审计和临床有效性承诺。

## 源码二刷

带着“边界在哪里执行”重读：

1. [`app/router/chat.py`](../../app/router/chat.py)：身份格式与可选 Token；
2. [`app/schemas/chat.py`](../../app/schemas/chat.py)：`query`、`session_id` 输入约束；
3. [`app/service/chat_service.py`](../../app/service/chat_service.py)：缓存、历史和长期事实可能接触哪些数据；

## 面试背板

> 我把项目定位为临床决策支持原型，而不是自动诊疗系统。输出只用于辅助核对；紧急风险必须绕过模型直接进入现实处置流程；开发测试只使用虚构或脱敏数据。现有身份头、共享 Token 和数据存储都是原型能力，生产化还需要真实认证授权、审计、数据治理和临床验证。

## 常见问题

**模型给出的内容看起来很专业，可以直接采用吗？** 不可以。表达流畅不等于证据完整或结论正确。

**只在自己电脑上运行就能输入真实病例吗？** 不能据此判断安全。输入仍可能进入日志、缓存、向量库或外部模型服务。

**界面写了免责声明就够了吗？** 不够。免责声明不能替代技术控制、流程控制和人工复核。

## 自测

1. 哪些紧急情况不应等待系统回答？
2. 为什么 `X-User-Id` 不是可信登录？
3. 哪些组件可能持久化病例相关内容？
4. “仅供参考”还需要哪些工程措施配合？
