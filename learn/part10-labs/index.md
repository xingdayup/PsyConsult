# Part 10｜扩展实战：测试先行，小步接主链路，随时可回滚

临床类原型最怕“文件写出来了，看起来也能运行，但用户入口根本到不了，失败时还拖垮整条链”。这一篇只练一种节奏：先把期望写成测试，做最小实现，再从 `/api/chat` 证明主链路可达，最后留下清晰回滚点。

## 学习目标

- 建立 RED→GREEN→集成→回归的改动节奏；
- 新增工具时同时验证纯逻辑、Tool 契约和 Agent 注册；
- 准确接入仓库现有但尚未进入主图的 MCP 基础代码；
- 设计路由、检索、SSE 与安全评测，不编造指标；
- 用小 diff、开关、降级和独立提交控制回滚风险。

## 类比：给运行中的医院增加新检查项目

新设备放进仓库不等于医生能开单；医生能开单也不等于接待入口可路由；设备故障时还不能拖垮其他会诊。因此每个实验必须回答：

1. **规格**：什么输入应得到什么稳定结果？
2. **可达**：从现有 Agent/API 哪条路径能调用？
3. **降级**：依赖不可用时保留什么能力？
4. **证据**：哪些测试和构建证明它工作？
5. **回滚**：撤掉哪些文件才能回到上一个稳定点？

当前事实必须先写在白板上：

- `DiagnosisAgentNode` 目前只注册同义词、Neo4j、Milvus 三个工具；
- `MCPManager`、`mcp_servers.json`、`clinical_tools.py` 已存在；
- `chat_service.init_agent_system()` 当前没有创建 `MCPManager`；

- 当前 pytest 在 `app/test/`，前端没有单元测试，门禁为 type-check + build。

## 源码二刷

每个实验结束后，从用户入口逆向二刷：`/api/chat → stream_chat → graph → node → tool`。只要有一段无法指到具体调用，就可能是孤立实现。再从关闭路径正向检查：连接、全局引用、后台任务和外部进程是否有清理策略。

## 面试背板

> 我扩展这类 Agent 系统时不从大改图开始，而是先把稳定契约写成离线测试。工具先测纯逻辑和注册，MCP 再测发现、注入、降级和关闭，最后从 API/SSE 证明可达。每一步控制 diff、跑全量回归并形成独立回滚点，避免“功能存在但主链路不可达”。

## 常见误解

- **“测试文件写完就算测试先行。”** 必须先看到因预期业务缺口而失败。
- **“工具能单独调用就完成接入。”** 还要注册、路由和入口证据。
- **“MCP 服务文件存在就已支持 MCP。”** 当前主图没有连接与注入。
- **“真实 LLM 最适合单元测试。”** 网络模型慢、贵且非确定。
- **“回滚就是删新增文件。”** 残留 import、节点和生命周期代码也要一起撤销。

## 自测

1. 什么样的失败才算有效 RED？
2. 如何发现“新工具文件存在，但 Agent 从不调用”？
3. MCP 连接为何应放应用生命周期，而不是同步构造函数？
4. API 层可能无需改代码时，怎样证明内部新能力已可达？
5. 没有基准数据时，面试中应怎样表达结果？
